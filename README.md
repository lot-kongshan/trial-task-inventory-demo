# 库存预占原型

> 演练提交：用于验证招聘实战任务系统的全流程，非真实候选人作品。

## 怎么跑

```bash
pip install -r requirements.txt
pytest -q                      # 3 个测试：并发不超卖 / 超时释放 / 确认后保持扣减
uvicorn app:app --reload       # http://127.0.0.1:8000/docs
```

## 做了什么

先做需求 2（原子预占防超卖）和需求 1（超时自动释放），再顺手做了需求 4 的一部分（确认支付，拦截已超时释放的预占）和需求 3（流水倒序查询）。

- `POST /stock/{sku}` 初始化库存，`GET /stock/{sku}` 查可用量
- `POST /reservations` 预占：全局锁内检查并扣减，库存不足返回 409
- `POST /reservations/{id}/confirm` 确认：只有未过期的 held 状态可确认，已释放返回 409
- `GET /stock/{sku}/movements` 按时间倒序返回流水（init / reserve / release_timeout / confirm）
- 测试：200 个线程抢 10 件库存，成功恰好 10 次

## 我的假设

- 「超时自动释放」不要求精确到秒的后台定时器：每次读写前惰性回收过期预占，效果对外一致，且不需要额外进程。
- 确认支付后库存不再变化（预占时已扣减可用量，确认只改状态）。
- 单实例部署即可验证机制，所以用进程内锁 + 内存存储。

## 没做什么及原因

- 需求 4 的「告警推送」没做：30 分钟内优先保证交易链路正确，告警渠道和阈值都不明确。
- 没有持久化：重启丢数据；生产要换成 PostgreSQL 行锁或 Redis Lua 原子扣减。
- 没有鉴权和幂等键。

## 已知风险

- 进程内锁只在单进程有效，多副本部署会超卖。
- 惰性释放意味着没有请求时过期预占不会被回收（对外查询时会先回收，结果仍正确）。
- 流水只在内存里，量大时查询是全表扫描。

## 再给 2 小时我会怎么做

换 PostgreSQL（`UPDATE ... WHERE available >= qty` 原子扣减）+ 后台定时回收 + 预占幂等键 + 低库存告警 webhook。
